Title: Unauthenticated websites can exfiltrate arbitrary local files through the EverOS API

Severity: High — CVSS 3.1 8.2 (AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:L/A:N)
Calculator: https://www.first.org/cvss/calculator/3.1#CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:L/A:N

Summary:
EverOS's FastAPI memory API has no authentication by documented design.
Two insecure defaults combine into browser-mediated local file disclosure:

1. file_uri_allow_dirs defaults to [] and the empty allowlist is treated as
   "allow any readable file". POST /api/v2/memory/add accepts a content item
   with uri file:///...; the file is read by the EverOS process, parsed, and
   stored as parsed_content, which POST /api/v2/memory/search returns
   verbatim (50 MB cap per item).

2. CORS defaults to allow_origins=["*"] with allow_credentials=True;
   Starlette reflects the request Origin and returns
   Access-Control-Allow-Credentials: true.

Any website a victim visits can therefore issue cross-origin requests to the
loopback API, ingest arbitrary local files readable by the EverOS process,
and read them back — no credentials, cookies, or prompt required.
Attacker-chosen memories can also be written (context poisoning).

Attack path: victim visits attacker page -> cross-origin POST
/api/v2/memory/add {"uri":"file:///etc/hostname"} -> EverOS stores parsed
content -> cross-origin POST /api/v2/memory/search returns it -> JS exfiltrates
to attacker collector. Demonstrated end-to-end in headless Chromium from a
distinct cross-origin hostname mapped to loopback.

Impact: arbitrary local file read (credentials, SSH keys, browser profiles,
documents) exfiltrated via the victim's browser; integrity impact via memory
injection. OS file permissions still apply.

Technical details, steps to reproduce, evidence captures, and runnable PoC:
